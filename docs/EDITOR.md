# The editor as built

Written 2026-10-05 for [plan 03](plans/03-editor.md). It records what exists, how it is put together, how to run and test it, and what is still open. The plan stays the statement of intent.

## Run it

```
npm install
npm run runtime -- install      # once: builds the SCRAM runtime the app needs (see RUNTIME.md)
npm start                       # builds the web app and serves it on http://127.0.0.1:5205
```

Development: `npm run dev:server` (the API on 5205, also accepting the Vite origin) and `npm run dev:web` (Vite on 5206, proxying `/api`), then open http://127.0.0.1:5206. Saved models live in `~/.sneed/models` (`SNEED_PROJECT_DIR`), runs in `~/.sneed/runs` (`SNEED_RUNS_DIR`); ports come from `SNEED_PORT` and `SNEED_WEB_PORT`. Without an installed runtime the editor still opens and edits, and Run says exactly how to fix it.

## Shape

| Piece | Where | What it does |
|---|---|---|
| Server | `src/server/` | Plain Node HTTP, bound to loopback only. `POST /api/validate` (problems plus the model and document hashes), `PUT/GET /api/models/<name>` (atomic saves of the exact text), `POST /api/run` and `/api/run/cancel` (one run at a time, cancel and browser disconnect both stop the engine), `GET /api/health` (is the runtime installed). Host and Origin checks, a custom header required on writes, a size limit, typed errors that never carry a path or stack, a strict content security policy on the pages. |
| Editor core | `src/web/model/` | No DOM. `doc.ts` (immutable edits that keep unknown fields), `visual.ts` (the drawn tree, repeated-reference markers, tidy layout, keyboard neighbours), `editor.ts` (selection, undo and redo, validation scheduling, runs, staleness, files). |
| Interface | `src/web/ui/` | Vanilla TypeScript and SVG in the suite's ribbon look, system fonts only. The drawing, an outline list (the accessible twin of the drawing), Properties, Problems and Results panels, dialogs. |

The browser runs no core code. Validation, hashing and analysis all happen on the server, through the same functions the tests use, so the editor cannot disagree with the engine pipeline.

## Behaviour worth knowing

- A basic event or gate is **drawn once**. Every further use of the same id is a dashed **repeated reference**; selecting either highlights the other. A OR A is shown as one event and one marker, and analyses to 0.1, not 0.19.
- The editor **allows what the validator will name**. A cycle, a one-input AND, a K outside 2 <= K < N or a missing reference can be drawn; the Problems list names each in plain words, selects the offender on click, and blocks Run. A probability outside 0 to 1 is refused at the field with the reason and never reaches the model.
- **Layout is separate from the model.** Moving a node changes the file but not the model hash, so a result stays current. A probability, structure, assumption or method change makes the result **stale** (a banner and a pill say so); undoing it makes it current again.
- Results show the probability with the stated assumptions, the cut sets (choose one to see it on the drawing in plain words), and how the number was produced. A rare-event sum above 1 shows the real sum with a caveat and the bound 1 as the probability. A failed, cancelled or truncated run shows reasons in words and never an unlabelled number.
- Keyboard: Tab reaches the drawing as one stop (roving focus); arrows move between nodes, Enter edits, Delete removes, `+`, `-`, `0` zoom and fit; Ctrl+Z, Ctrl+Y, Ctrl+S, Ctrl+Enter, Escape (cancel a run, clear a highlight, clear the selection). Everything is also reachable by pointer: drag a node, drag from the dot under a gate to connect.

## Lessons (plan 04, built 2026-10-05)

- **Files.** `lessons/*.json` (schema in `src/core/lesson.ts`). Each lesson has steps, expected outcomes, "check this" detectors and a hand calculation. An outcome names an entry in `tests/oracles.json` and must equal it; the loader refuses anything else, and the server (`GET /api/lessons`) serves no lesson at all if one file or the oracle file is bad (503 `E_LESSONS_UNAVAILABLE`). The server reads the oracle file from the source tree, so lessons need the repository layout.
- **Checker.** Declarative checks on structure and numbers only; position on the drawing is never read. The editor shows each node by its display name when that name is unique, because the editor's ids are E1, E2 and a student names an event P1. A lesson is complete only when every step is done, no "check this" detector fires **and** a current, completed, complete engine result equals an expected outcome (names, not ids, in the cut sets). A stale, truncated or failed result is never credited.
- **Panel.** The Lesson tab lists the lessons; starting one replaces the model with an empty one (asking first if there is unsaved work). Progress is stated in words (Done, Next, Not yet), not by colour. The hand calculation stays hidden until the student has run the model once.
- **Review.** `docs/LESSON-REVIEW.md` (generated by `node scripts/lesson-review.mjs`) is the sheet for an instructor. **No instructor has reviewed the lessons.** The author's own read and a readability score (about grade 4 to 5 by Flesch-Kincaid) are not a review.
- **Tests.** `tests/unit/lesson.test.ts`, lesson blocks in `web-editor.test.ts` and `server.test.ts`, `e2e/lessons.spec.ts` (lesson 1 by keyboard alone; lessons 2 and 3 with the real engine), a lesson case in `e2e/a11y.spec.ts`, and `python tests/mutation/verifier_mutations.py lessons` (15 mutations, all caught).
- **Known gaps.** Events must be named as the steps say (the panel says so when a result does not match). No screen-reader pass. Lessons only teach the static tree: no figures, so no alt text yet.

## Common-cause groups (plan 15, stage C4, 2026-10-25)

- **Make a group.** Select a basic event, and in its Properties tab use "Common-cause group": choose another event that is in no group and press "Make a group", or add the event to an existing group. A group is named by its ID (`CC1`) or by the name the student gives it. Beta starts at 0.1.
- **The group.** Selecting a group (a click on its box in the drawing, or its entry under "Common-cause groups" in the outline or in the model properties) shows its name, beta (0 to 1, refused at the field otherwise), the members, the numbers `(1 - beta) x Q` and `beta x Q`, and buttons to add or take out a member and to delete the group (the events stay). A group needs two members, so taking out one of two removes the group, and deleting a member event does the same. The members share one probability: changing it for one changes it for all. The assumptions of the model follow the groups (`beta-factor-groups` or `declared-independent`), so the editor never makes the mismatch `E_CCF_ASSUMPTION`.
- **Drawing.** A dashed box with the group's name and beta behind its members, and a tag with the group's name on each member node. A box round members that are far apart also covers other nodes, so the tag on the node, not the box, says who belongs. The printable figure and the SVG/PNG export draw the same (dash-dot box, "in <group>" under each member, a line per group, and an assumptions sentence that does not say "independent").
- **Result.** The Results tab says "Common-cause groups used (beta-factor)" with each group, and reads the answer against the independent one: "If these events failed independently the probability would be X. With the groups it is Y, which is higher/lower." The independent value is worked out by the built-in engine (a second solve of the same events without the groups); the SCRAM path does not work it out and the panel then says so. The cut sets use `G.CCF` (the common cause) and `A.independent`; the table explains them and "Explain" speaks of "the common cause of group G".
- **Compare** lists groups added, removed or changed (beta, members) as differences in the model.
- **Lesson 5**, "Pumps that fail together" (`lessons/05-common-cause.json`): AND without and with a group (0.01 then 0.018019), then OR (0.180181 against 0.19). The student names the events A and B and the group G, as the other lessons ask. Its outcomes are the frozen oracles `cc-and` and `cc-or` of `tests/oracles-common-cause.json`; the server reads that file beside `tests/oracles.json`.
- **Tests.** `tests/unit/ccf-editor.test.ts` (the document operations, the commands, the figure, the comparison and lesson 5 done through the editor with the real built-in engine), `tests/unit/lesson.test.ts` (the lesson against the exact evaluation of the group definition), `e2e/common-cause.spec.ts` (the real page: make a group, the box and tags, beta, run and read the result, undo, keyboard only from the outline, lesson 5 to completion, and an axe audit of two states).
- **Not done.** Dragging an event into a box, and a ribbon button for groups. The mutation checks of the drawing, the properties panel, the outline and the results panel (they need the browser suite, which the mutation script runs with Chrome): only the model and logic code is mutation-tested.

## Compare (plan 03, built 2026-10-05)

- **Data.** (Codex review fixes, 2026-10-05: no link below the runs folder is followed, even one pointing at another run; the model file must be JSON; a record without status or a cut-set list is unreadable and is never shown as "zero cut sets"; each run's own status and completeness are always stated and a run that is not completed and complete is called diagnostic only; "same inputs" needs the method, the engine name, version and build and the model hash stated in both records; a slow answer to an older comparison cannot replace a newer one; a failure to list runs is shown as that.) Every run is already saved in its own folder (`native/model.json` byte for byte as submitted, `results.json`). `GET /api/runs` lists the newest 100 readable runs; `GET /api/runs/:id` returns one run's model text and record. Read-only: ids are plain folder names (path tricks are refused), a damaged run is left out of the list and answers 422 if asked for directly, and nothing in these routes writes.
- **Diff.** `src/core/compare.ts` (pure, hostile-data safe). Model: top event, events and gates added or removed, changed probabilities, names, gate types, vote thresholds and inputs (input order is not a difference; a repeated input is). Result: status, completeness, method, engine, the probability change (with a ratio only when the earlier value is not zero), cut sets only in one run or with a different probability, and assumptions that differ.
- **No judgement.** The view says "then", never better, worse or safer. When two runs analysed the same model with the same method and engine and the numbers still differ, it says so as unexpected and tells the reader to treat both as unverified.
- **Panel.** The Compare tab. Until a student picks a run, the choice follows the two newest runs as new ones arrive; a choice they made is kept while it stays on offer.
- **Tests.** `tests/unit/compare.test.ts`, run-route tests in `server.test.ts`, compare blocks in `web-editor.test.ts`, `e2e/compare.spec.ts` (including a keyboard-only run), an axe case, and `python tests/mutation/verifier_mutations.py compare` (14 mutations, all caught; the dirname check in `runs.ts` is defence in depth and has no mutation because the id pattern already refuses every path).
- **Screen reader.** `docs/SCREEN-READER-PASS.md` is the script for a human. No pass has been done.
- **Gotcha.** The mutation runner builds `dist/web` from each mutated source, so `dist/web` is left as the last mutant. Run `npx vite build` after any mutation run before using the app or a bare `playwright test`.

## Queued runs and saved-run reuse (built 2026-10-06)
- **Queue.** The server runs one analysis at a time. A second `POST /api/run` waits its turn (up to 8 waiting; the ninth is `409 E_BUSY`) instead of being refused. A client may name its request (`request_id`, 1 to 64 of `A-Za-z0-9_-`); `GET /api/run/status` lists who is running and who waits, and `POST /api/run/cancel` with a `request_id` cancels exactly that request (a waiting one is removed and answered `{kind:'dequeued'}`; without an id the running one is cancelled, as before). A waiting client that disconnects leaves the queue and never runs. The editor shows "Waiting for N other runs" while it waits.
- **Reuse.** Before running, the editor asks `POST /api/run/lookup` whether a complete saved result exists for exactly this run: same model (by `model_hash`), method, and engine build (built-in: name and version; SCRAM: version and the hash of the binary the installed runtime resolves to), `status` completed and `completeness` complete, searching the newest 1000 runs. If so it **offers** it ("Show the saved result" or "Run again") instead of running; nothing is run or written until the student chooses. "Both" is never offered (the cross-check is not saved). A shown saved result is labelled as one. The built-in engine's build is the hash of its source files (see docs/ENGINES.md, "Engine identity"), so a changed solver is never offered an old result, whether or not the version was bumped; records made before this was recorded (no build) are not offered.
- **Tests.** Server queue and lookup tests, editor tests, 3 e2e cases (`e2e/reuse.spec.ts`, plus an axe case), 33 mutations (`verifier_mutations.py queue`). The e2e `run()` helper chooses "Run again" when the offer appears, because the server keeps every run.

## Print and image export (built 2026-10-06)
- **Figure.** `src/web/model/figure.ts` turns the drawing into one standalone SVG document (pure text: no fonts, scripts, external files or colour; ellipse = basic event, rectangle = gate, dashed = a repeated use). Below the drawing it states the assumptions and, when there is one, the result: probability, method, engine, status, cut set count, the cross-check (agreement, disagreement or no second opinion) and the model hash. A run that is not complete/completed is headed **DIAGNOSTIC ONLY** with its reasons. A result that is out of date, or for a model edited since it was checked, is **not** shown: the figure says "NO CURRENT RESULT". The same input gives the same bytes; a date appears only if one is passed.
- **Export.** Ribbon group Export: **SVG** (a download, checked to parse as SVG first), **PNG** (the browser draws that SVG at 2x, at most 8000 px a side) and **Print**. Names and the model name are escaped; characters XML cannot hold are replaced. Print builds a sheet on `beforeprint` (so Ctrl+P prints the same): the figure plus a table of the minimal cut sets (first 60), and the editor itself is not printed.
- **Tests.** `tests/unit/figure.test.ts` (31 cases), editor cases, `e2e/export.spec.ts` (SVG parses in the browser, PNG is a real PNG with ink, stale result not drawn, print media shows only the sheet and a PDF is made, keyboard names), 35 mutations (`verifier_mutations.py export`). Codex review found two real defects (the cross-check was dropped from the figure; XML-invalid characters made an unparseable file) and both are fixed.
- **Not done:** a PDF button (use the browser's Print to PDF); standard gate symbols (gates are labelled rectangles); the figure has not been looked at by a human for layout on a very large tree.

## Importance measures (plan 12, built 2026-10-06)
- **What.** In the Results tab, "Compute importance" gives, for every basic event that can reach the top, four exact measures: **Birnbaum**, **risk achievement worth**, **risk reduction worth** (shown as ∞ when setting the event's probability to zero makes the top probability zero) and **Fussell-Vesely** (exact form). Definitions, assumptions, hand oracles and limits: [docs/plans/12-importance.md](plans/12-importance.md). The table is never automatic, is for the model on screen only (any edit hides it), is sorted by Birnbaum, and carries the definitions and the assumptions. Built-in engine only; SCRAM is not asked and the result record is unchanged.
- **How.** `POST /api/importance` runs in a worker thread with the solver's time and memory limits, takes its turn in the same queue as runs, and can be cancelled (button, or by request id). At most 300 events and a work budget (events x diagram nodes); beyond that a stated refusal, never a partial table.
- **Numerical honesty.** Birnbaum is computed on the "false" side when the top event is almost certain (an OR of 16 events near 0.9 has Birnbaum about 1e-16 per event, which a plain difference rounds to 0); Fussell-Vesely is p x Birnbaum / P; a probability that underflows although the event can matter, or any non-finite measure, is a `numeric-range` failure with a message, and "impossible" is decided structurally.
- **Tests.** Hand oracles, agreement with the exact-rational enumeration oracle on the frozen models and 1000 random trees, derivative and identity checks, edge cases and limits, server, editor and 4 e2e cases plus an axe case, 39 mutations (`verifier_mutations.py importance`). Codex found 4 real defects (cancellation in Birnbaum/FV, underflow reported as success, no cancel from the editor, a false structural explanation of infinity); all fixed.
- **Not done:** SCRAM parity (the pinned build has no such output for this model class), importance for approximation methods, groups of events, measures with uncertainty. Plan 07 said P4 waits for P3 verification; the human screen-reader pass and instructor review are still open.

## Event trees (plan 13, stage S3, built 2026-10-06)
- **Where.** The title bar has a **Fault tree / Event tree** switch (a group of two toggle buttons). The Event tree view replaces the drawing and the side panels; the ribbon and the Run controls of the fault-tree editor are hidden while it is open, and Ctrl+S, Ctrl+Enter and Escape act on the event tree. The fault-tree editor's state is kept untouched underneath. Switching to the view re-reads the saved models, because the model may have been saved again in the other view.
- **Table first.** Everything is a labelled form or table that the keyboard and a screen reader can walk: the initiating event (name, description, **frequency per year**), the saved fault-tree model the headings refer to, the **headings** (order, name, the model's event or gate whose occurrence is the failure, "Asked: always / only if an earlier heading worked or failed", Up / Down / Remove), the **end states** (name, description, "example" box, how many sequences end in it), and the **sequences** (every path the headings allow, listed for you, with one end-state choice each). A heading that is not asked on a path is left out of that path. At most 12 headings. There is no drawing yet (stage S4).
- **The sequence list is generated.** After any change to the headings or to when they are asked, the editor regenerates the complete list of paths. A path that still exists keeps its end state. A path that does not exist is gone and a new path has none: the editor does not carry an answer over to a different path (that would be a guess), and it says how many choices were dropped. Every sequence needs an end state before the tree can be analysed ("Give them all: choose…" fills the empty ones). Heading and end-state ids are generated (`H1`, `ES1`) and not editable, so a path can never name something that was renamed.
- **End states are named by the author.** A new tree starts with one end state called "End state 1 (example)", marked as an example. The editor never offers "core damage" or any other plant condition as a default.
- **Checks.** The whole document is sent to `POST /api/event-tree/validate` after each edit (debounced); its problems are listed with their codes (`E_NO_END_STATE`, `E_STALE_MODEL`, ...). **Analyse** is available only when the text on screen has been checked and has no errors; the pill beside it says why not. A frequency that is not a number is refused in the field, with the message next to it, and the document keeps the last good value.
- **Analyse** runs `POST /api/event-tree/run` with a request id, takes its turn in the same queue as runs and importance (the pill shows "Waiting for N other runs…"), and can be cancelled (button, Escape, or by request id). "Also show the 'success branches ignored' approximation" is off by default; when on, the result table gets two extra columns and a labelled note that it is a different kind of number whose sum is not the initiating-event frequency.
- **The result** shows the total frequency, the sequence table (path, end state, probability of the path, frequency per year), the end-state table ("(example)" beside example states), the partition check in words (the sequence probabilities add up to 1, and the difference), the assumptions block with its plain-language paragraph, the caveats and warnings, the engine and build, and both hashes. A failed or cancelled analysis shows the named reason and no numbers.
- **Stale handling.** A result is current only for the tree it was made from. It is marked **out of date** when the tree's meaning changes (the hash, which ignores names, descriptions and timestamps), when the approximation setting changed, and, until the new text has been checked, after any edit. When the saved fault-tree model is saved again, the document is named stale by the check (`E_STALE_MODEL`), a banner says the model changed, and Analyse stays blocked until the author presses "check against the current model" (pinning the document to the new hash); the old result remains marked out of date. The editor does not do this for the author.
- **Files.** Event trees are saved in the `event-trees/` folder beside the models (`New / Open / Save / Save as`, with the same guards as models: unsaved work is confirmed before it is discarded and the tab warns before closing).
- **Code.** `src/web/model/event-tree-doc.ts` (pure edits), `src/web/model/event-tree-editor.ts` (state, no DOM), `src/web/ui/event-tree.ts` (view), `src/core/event-tree-paths.ts` (the path rules, shared with the validator and the engine: the browser cannot import the validator, which reads files).
- **Tests.** 34 unit tests (document edits including a random-edit property test that every edited document, once its sequences have an end state, passes the server validator; the editor with a fake API: queue, cancel by request id, stale rules, model changes, late answers) and 8 e2e cases built on plan 13 case 6.2 (the shared-event numbers 0.077 / 0.063 / 0.108 / 0.252 per year are read off the page; the approximation 0.14 and ratio 2.22; a model saved again; save and reopen; bypass and ordering; keyboard-only; Ctrl+S saves a field still being typed in), plus an axe audit of four states. 43 mutations of the document edits and the editor (`verifier_mutations.py etui`); the view itself is covered by the e2e and axe tests, not by mutants. The axe audit found two real problems on the way (no main landmark when the fault-tree view is hidden; a scrollable results region with nothing focusable in it) and one older one (white-on-grey primary buttons while hovered), all fixed. Codex review (silent-failure): 8 findings, all real and fixed: a slow save overwrote edits made meanwhile or touched a newly opened tree, New/Open/model choice answers could replace a newer document, keyboard Save and Analyse ignored a field still being typed in, a frequency that is not a number left a result "current" and Analyse on the old value, a failed model check or cancel was silent, and action buttons lost keyboard focus on re-render.
- **Not done:** undo and redo in this view; the three lessons (S5); a headless verb. The human screen-reader pass and instructor review still apply to this view too.

## Event tree drawing, files, print and Compare (plan 13, stage S4, built 2026-10-07)
- **The drawing.** Under the Sequences table, the same tree as a picture: the initiating event on the left, one column per heading with a **works** branch above and a **fails** branch below, and one line per sequence on the right with its number, its end state and, only while there is a current complete result, its frequency per year. A heading that is not asked on a path has no branch there (it is passed over). It is a picture of the tables, not a second source: every number is a row of the result, and the tables hold exactly the same information in an order the keyboard and a screen reader can follow (the drawing itself is one labelled image, not a second keyboard interface). Black on white, shapes and words, no colour. More than 64 sequences are not drawn: the figure says so and the table lists them all. `src/web/model/event-tree-figure.ts` (pure text in and out, like the fault-tree figure; the same bytes for the same input).
- **Never a wrong number on the picture.** The figure draws frequencies only from a result that is complete and for the tree on screen. An old result gives "NO CURRENT RESULT" and no numbers (an edit not yet checked counts as old); a failed or cancelled or incomplete result gives "DIAGNOSTIC ONLY" and the named reason. The approximation, if computed, is mentioned and not drawn: it is a different kind of number. The caption always carries the headings in words, the assumptions paragraph, the partition check and the caveats.
- **Files.** SVG and PNG buttons save the figure (well-formed SVG, checked before it is offered; the PNG is drawn by the browser from that same figure, at twice the size or less if that would be too large for a canvas). Print builds a sheet (only while printing) with the figure, then, for a current result, the sequence table and the end-state table with full-precision numbers, so a printed page holds every number. Ctrl+P prints the same thing; in the fault-tree view it still prints the fault-tree sheet.
- **Saved analyses.** `GET /api/event-tree-runs` lists the newest 100 folders under `runs/` that hold an `event-tree-results.json` of kind `sneed.event-tree-result` version 1 (a folder that cannot be read, is of another kind or version, is a link, or is over 4 MB is left out, never an error for the rest); `GET /api/event-tree-runs/:id` serves the record. Same name rules, link handling and status codes as the fault-tree runs, which never see these folders, and read only. Nothing here changes the record or anything SEED reads.
- **Compare.** Under the results: two selects (earlier and later; until chosen they follow the two newest analyses), Compare and Clear. `src/core/event-tree-compare.ts` reads two records without trusting their shape and reports: what the analyses were made from (same tree, same fault-tree model, same engine build: "the numbers should be identical, any difference is unexpected"), the initiating event (name, frequency), headings added, removed or changed, the total frequency, every sequence whose frequency or end state changed (from, to, difference, ratio) or that exists in only one, end states likewise, and assumptions that differ. **Numbers are compared only when both analyses are complete**: a failed or cancelled analysis has none, and "every sequence was removed" would be false, so only the inputs are compared and the view says so. A ratio from zero is "n/a", never infinity. Nothing says one analysis is better or safer.
- **Tests.** 15 figure tests (lines per sequence, bypass, stale/old/failed/incomplete results, limit at exactly 64, hostile names, deterministic bytes, each frequency beside its own sequence, an invalid frequency entry not drawn), 14 compare tests (including hand-edited and damaged records, and engine builds that share a 12-character prefix), 10 saved-run tests (listing, limit, inspection budget, bounded strings, kinds, links, size, traversal, read-only) and 6 editor tests for the compare state, 7 e2e figure/export/print cases and 4 e2e compare cases on plan 13 case 6.2 (S = 0.1 then 0.2: the "both fail" frequency goes 0.077 to 0.124 per year, x1.61039; a damaged saved analysis is named), an axe audit of the drawing and of two comparisons, and 52 mutations (`verifier_mutations.py ets4`), whose survivors found a real defect on the way (a result that was completed but not complete was still drawn as numbers) and gaps in the tests. Codex reviews (silent-failure on the browser and compare code, security-boundary on the new routes): 6 findings, all real, all fixed: a comparison could stay on show under a pair of analyses it was not made for; a record that says it is complete but has a damaged row or no total was compared as if sound (now: not compared, and named); "same engine build" was claimed from a 12-character label or from no hash at all (now: the full build hash, and unknown when it is not recorded); the drawing showed the last good frequency while the field held something that is not a number; and the listing could open an unbounded number of files and return unbounded strings (now at most 400 files opened and every string cut short).

## Event-tree lessons (plan 13, stage S5, built 2026-10-07)
- **Three lessons**, in a "Lessons" section at the top of the Event tree view's side column (a closed `details` until a lesson is open): (1) *An event tree by hand: two independent safety functions* (plan 13 case 6.1: multiply along each path, the frequencies add up to the initiating-event frequency, end states grouped by how many headings failed); (2) *When two safety functions share a cause* (case 6.2: **predict first**, then see the exact frequency of "both fail" beside the product of the two failure probabilities, which comes out about a third too low); (3) *A heading that is not always asked* (case 6.4: bypass). Probabilities are made up and the assumptions text of each says so, says that frequencies are not plant figures, and says that end states are examples.
- **Format.** `lessons/event-trees/*.json`, kind `sneed.event-tree-lesson` version 1 (the fault-tree lessons stay in `lessons/`): title, goals, assumptions, `model` (the fault-tree model the lesson saves, with its name), optional `prediction`, `steps` (each with a prompt, a hint and a check), `outcomes`, `mistakes`, `hand_calculation`, and `discussion` (the instructor's questions and model answers). Checks: `frequency`, `heading-events` (the events the headings fail on, in order), `sequence-count`, `end-states-min`, `ends-assigned`, `ends-by-failures`, `bypass`, `prediction`. Detectors ("check this"): two headings on one event, a heading on a named event (the model's top event), a frequency of zero, the wrong branch of a bypass. Everything is checked against the student's document and never against anything drawn; heading names, heading ids and end-state names do not matter, only the events and the numbers.
- **Expected numbers are never computed by the app.** Each outcome names an entry of `tests/event-tree-oracles.json` (model, initiating frequency, headings, every sequence's probability and frequency, a hand derivation). The server loader **refuses all event-tree lessons** if that file is missing, and refuses a lesson whose outcome differs from its entry, whose model is not the entry's model or is not a valid fault-tree model, whose steps ask for a frequency, headings, sequence count or bypass other than the entry's, whose prediction names a sequence the entry lacks, whose outcome lists a sequence twice, whose model name is not a model name, or that shares an id with another lesson. A test re-derives every number of the oracle file by exact rational enumeration (sharing no code with the engine) and compares the engine with it. Results are keyed by the EVENTS on a path ("X:fails,Y:works"), so a student's own heading ids do not matter.
- **Complete means all of these**: every step done, no mistake showing, an analysis that is **current, complete, made with the lesson's own fault-tree model (by hash: an unrelated model that happens to give the same numbers does not count)** and whose every sequence frequency equals the outcome's to 1e-12, and, for a lesson with a prediction, **a prediction that was typed when that analysis was started**. The prediction is kept with the analysis: a guess typed after the result, or while it ran, or before a rerun that failed, changes nothing beside an earlier result. A student who wants to can always rerun with the answer typed in; the prompt is for reflection, not assessment, and the lesson says there is no wrong guess.
- **The reveal** (shared-event lesson) uses numbers from the student's own analysis: the probability that each named heading fails (summed over the paths on which it fails), their product times the initiating-event frequency, the exact frequency, and how far below it the product is (32.7 percent for the lesson). It is an explanation, never a grade, and says that the product is right only when the headings fail independently. Predictions are only about sequences in which the named headings all fail.
- **What starting a lesson does**: saves the lesson's fault-tree model under its own name (`lesson-et-independent`, `lesson-et-shared`) and puts a new tree on the screen that refers to it, with the first heading on the model's first event and a placeholder frequency of 1; none of the answer is filled in. **A saved model with that name that is not exactly the lesson's model is never replaced**: the lesson then uses `-2`, `-3`, ... and says so. Unsaved work is confirmed first (as for New). A start that was overtaken, or during which the tree was edited, changes nothing. An analysis that comes back after another tree was put on the screen is not shown and does not unlock the hand calculation. New and Open end the lesson. The hand calculation is shown only after the student has analysed.
- **The instructor's questions and model answers never reach the browser**: the route `GET /api/event-tree-lessons` removes `discussion` before sending, and a test asserts the response text does not contain it.
- **Instructor sheet.** `docs/EVENT-TREE-LESSON-REVIEW.md`, generated with `node scripts/lesson-review.mjs` (the fault-tree sheet `docs/LESSON-REVIEW.md` is unchanged and unaffected): per lesson the goals, assumptions, the model, steps, prediction prompt, expected frequencies, "check this" messages, hand calculation, the instructor's discussion questions with model answers, and a reviewer block; `--check` exits 1 when a sheet differs from what the lesson files produce, and a test runs it (a sign-off applies to the text of the sheet). **No instructor has reviewed these lessons; that is the owner's.**
- **Tests.** 40+ unit tests of the checker, the refusals (each malformed field, each disagreement with the oracle, duplicates, unrelated models, predictions after the result), the loader and the route; 4 oracle tests (independent exact enumeration and the engine against every entry); editor tests for lesson state (start, naming, overtaken start, late analysis, prediction kept with its analysis, completion needs the lesson's model); 10 e2e cases (each lesson worked through the real page, wrong work not credited, the prediction flow, the mistakes, unsaved-work guard, a saved model with the lesson's name, keyboard only) and an axe audit of the list, a lesson in progress, a mistake, and a completed lesson with the reveal and hand calculation; 54 mutations (`verifier_mutations.py etlesson`; two removed as equivalent with reasons). Codex reviews (specification-gap on the lesson design and checker, silent-failure on the editor, panel and route): 10 findings, all real, all fixed: an unrelated model could complete the bypass lesson; a lesson listing one sequence four times passed the oracle check; a prediction typed after the result earned the credit; the end-state grouping of lesson 1 was not checked; a prediction about a "works" branch got the wrong comparison; starting a lesson overwrote a saved model; a start could throw away edits made meanwhile; a late analysis could unlock the hand calculation; the prediction shown could be paired with an older analysis after a failed rerun.
- **Not done:** the instructor read, the screen-reader pass over the lessons, a headless verb, undo and redo in the Event tree view.

## Undo and redo in the Event tree view (built 2026-10-07)
- **What is a step.** Every edit of the event-tree document: renaming, the initiating event, adding, removing, moving or editing a heading, changing when a heading is asked, adding, removing or editing an end state, choosing an end state for a sequence (or for all the unset ones), choosing the fault-tree model, "check against the current model". An edit that changes nothing is not a step. Each step has a name (`Undo: adding a heading`), shown on the button and announced in the status message ("Undid: adding a heading." / "Redid: ..."). Up to the last 200 steps are kept.
- **What is not.** Saving (it only stamps the time), running or cancelling an analysis, the approximation box, and the prediction box of a lesson. A frequency typed that is not a number is its own first undo step: Undo drops it and the field shows the last good value again.
- **Where history ends.** New, Open and starting a lesson give the new document its own history: undo never goes back into another document, and never ends a lesson (a lesson's progress follows the document, so undoing the edit that did a step un-does that step).
- **Buttons and keys.** Undo and Redo in the toolbar (disabled when there is nothing to do), **Ctrl+Z**, **Ctrl+Y** and **Ctrl+Shift+Z** when focus is not in a text field. In a text field Ctrl+Z is the browser's own undo of what is being typed (a field only commits when you leave it or press Enter). The buttons commit a field you are still typing in first, so Undo undoes the edit you just made rather than the one before it.
- **Results follow.** An analysis is current again when undo brings back the tree it was made for (the check is the hash of what the tree means), and old again on redo. Undoing the choice of fault-tree model reloads the model's events for the headings.
- **A bug the tests found on the way.** A text field that was typed in and then undone kept showing the typed text, because the view redrew only when the document differed from the last one it drew, and undo brought back an equal document. The editor now counts every change, undo and redo (`revision`) and the view redraws on it.
- **Tests.** 13 editor unit tests (labels, every kind of edit undone and redone to exactly the same text, no-op edits, removed headings and their end states restored, the draft, history ends, the cap of 200, saving, the model, results, lessons, the revision) and an end-to-end case (buttons with names and disabled states, keys outside and inside a field, the button committing a half-typed field, New starting afresh); 37 mutations with the headless verbs (`verifier_mutations.py etundo`).
- **Not done:** history that survives a reload or a save-and-reopen.
